历史已结算数据（数据源同步）

台账中的「历史结算」快照行：数据源一变即自动刷新

历史已结算数据来自数据源：① 应收单池（模板导入的 已结算金额、已结算金额(本位币)； 无该列时按 未结算折本币 反算）；② 外部接口地址（按间隔定时拉取）；③ 上传 JSON / CSV 文件。 三类记录按应收单号去重（外部数据源优先）后整体刷新台账中的「历史结算」快照行。
外部文件字段（中文表头 / 英文键名均可）：应收单号、已结算金额、结算日期、 客户、合同编号、应收金额、结算单号、核销状态、备注。 CSV 示例见 samples/历史已结算数据示例.csv。
「历史结算」行为来源系统既成事实的快照：不占用应收单余额（余额口径已体现在应收单的「已核销」）、 不可反核销、可随数据源刷新；纠错请修正数据源后重新同步。

反核销

导入财务应收单（按模板）

支持 .xlsx / .csv

模板结构（对齐 数据模板-财务应收单.xlsx 的「列表数据」表）：第 1 行为中文字段名表头（69 列）， 第 2 行起为数据行。列顺序可调整、可增删无关列，程序按字段名识别；「单据编号」为空时自动编号。

模板未含客户税号列，可另选客户档案文件（编码 + 统一社会信用代码）一起导入以补全税号； 未补到时匹配降级为合同号 + 金额。

匹配与复核规则（摘自 PRD）

1. 匹配优先级

购买方税号 → 合同编号 → 不含税金额 → 购买方名称（仅展示）。

2. 置信分档

分档判定条件系统动作复核人操作
高置信税号一致 + 金额在容差内自动预绑定一键/批量确认
中置信合同号一致或提取失败，金额在容差内但税号缺失/不匹配预绑定并高亮差异点逐项核对后确认或改绑
未匹配金额超容差，或无同合同同客户应收单不自动绑定，进人工池手动关联或标记异常

3. 金额容差

  • 差额 ≤ 0.01 元：四舍五入差，计入高置信。
  • 差额 0.01 ~ 1 元：降为中置信，界面标红显示差额。
  • 差额 > 1 元：不自动匹配，进未匹配池。
  • 一对多/多对一时，用发票组与应收单组的合计金额套用同一容差。

4. 多对多处理

  • 单对单：金额容差内自动预绑定。
  • 一对多（合并开票）：自动推荐组合，人工确认。
  • 多对一（拆分收款）：自动推荐组合，人工确认。
  • 多对多：不自动组合，仅列出同合同号、同税号候选，由人工圈选。

5. 合同编号提取

从备注按正则 合同\s*[编号]{0,2}\s*[：:]\s*([A-Za-z0-9\-_·]+) 提取，全角/半角冒号均可，提取结果原样保留（含 -、· 等字符）；仅在与应收单比对时使用规范化比较键。提取失败视为未知，降级为税号 + 金额匹配。

6. 发票 XML 解析

  • 数电票（根节点 <EInvoice>）：购买方税号取 BuyerInformation/BuyerIdNum，不含税金额取 BasicInformation/TotalAmWithoutTax（多明细时为合计），税额 TotalTaxAm，价税合计 TotalTax-includedAmount，开票日期 TaxSupervisionInfo/IssueTime，备注 AdditionalInformation/Remark；明细行 IssuItemInformation 支持多行。
  • 通用 <Invoice> 平铺结构：按标签名宽松匹配（购买方纳税人识别号 / BuyerIdNum / InvoiceNo / 金额 …）。
  • 一个文件内可含多张发票，全部导入；数电票无「发票代码」，该列显示 -。

7. 异常分支

  • 重复导入同一张发票（代码+号码）→ 拦截，不进匹配。
  • 备注无合同编号 → 降级税号+金额；仍无匹配进人工池。
  • 金额超容差 → 标红差额，进未匹配池。
  • 一张发票多候选 → 按金额合计排序，人工选择。
  • 发票后续作废/退票 → 标记异常，可追溯，不自动反冲。

8. 应收单导入（按模板）

  • 模板对齐《数据模板-财务应收单.xlsx》的「列表数据」表：第 1 行中文字段名表头（69 列），第 2 行起为数据；按字段名识别列，列顺序可调整、可增删无关列。
  • 所有字段原样保留：含 -、(、)、· 等字符不做裁剪；点击应收单行可展开查看全部原始字段。
  • 合同号取 合同号 → 合同(编)号 的原值；仅在与发票比对时使用规范化键（去空格/连字符并大写），原值不受影响。
  • 金额口径可选：默认不含税「金额」（与发票「不含税金额」同口径），亦可切换为含税「应收金额」；取不到时按税额/数量单价反算。
  • 剩余余额取「未结算折本币 / 未结算金额」，无值时视为全额未核销。
  • 模板不含客户税号列，可另选「客户档案」（编码 + 统一社会信用代码）文件一起导入补全税号；补不到则降级为合同号+金额匹配。
  • 金额为负的红字/冲销单据正常导入并保留原值，但不参与自动匹配。
  • 重复导入同一「单据编号」→ 拦截并在导入提示区列出。

9. 核销台账与反核销闭环

  • 台账只追加：核销记录写入后不修改、不物理删除；纠错一律走「反核销」。
  • 配分明细：每笔核销按「发票 × 应收单」逐行配对（pairKey = invoiceId:arId），记录本行核销额与核销前 / 后余额；一对多、多对一、多对多均可见每张发票抵了哪张应收单多少。
  • 金额守恒：Σ 明细核销额 = 台账核销总额；已核销 + 剩余余额 = 原金额（容差 0.01 元）。
  • 入库二次校验：写入前重新读取台账中有效记录的累计核销额，校验应收单余额是否仍然足够；发票已核销则拦截（INVOICE_ALREADY_WRITTEN）。
  • 幂等：同一 idempotencyKey 重复提交只入库一次，重复请求返回原记录。
  • 反核销（无需审批）：生成反向记录（金额取负、refBatchNo 指向原批次、明细逐行取负且 pairKey 不变），原记录置「已反核销」，应收单余额与状态回滚，发票回到「待匹配」重新参与匹配；同一记录只能反核销一次（禁链式）。
  • 原因码必填：WRONG_AR / WRONG_INVOICE / AMOUNT_ERROR / DUP_ENTRY / OTHER，连同操作人与时间一并留痕。
  • 期间关账：原核销所属会计期间已关账时，禁止直接反核销（PERIOD_CLOSED），应改走当期红冲（本期未开放）。
  • 持久化：原型优先使用 IndexedDB，不可用时降级 localStorage / 内存；设置 window.WRITEOFF_API_BASE 即切换为后端 HTTP 接口（Store 契约一致，UI 无需改动）。
  • 字段口径：业务日期 bizDate 决定会计期间，独立于操作时间；金额口径 amountMode（不含税 / 含税）在台账内隔离，不混用。

10. 历史已结算数据同步与台账自动刷新

  • 历史数据源：① 应收单池（模板 已结算金额 / 已结算金额(本位币)，无该列时按 未结算折本币 / 未结算金额 反算）；② 外部接口地址（JSON，可定时拉取）；③ 上传 JSON / CSV 文件。
  • 去重与优先级：三类来源按应收单号去重，外部数据源（接口 / 文件）优先于应收单池派生值；每条应收单最多一条历史结算记录。
  • 台账呈现：写入 entryType = 'HISTORY' 的「历史结算」行，method = 历史结算同步，来源列显示同步来源，可按类型 / 关键字筛选与导出。
  • 与核销事实隔离：历史结算行不计入 arWrittenOff()（应收单余额口径已包含数据源已结算额）、不占用发票唯一性、不计入「有效核销净额」；汇总单独展示「历史已结算（数据源）」。
  • 不可反核销：历史结算是来源系统既成事实，仅提供「修正数据源 → 重新同步」路径；台账「只追加」约束仅适用于本系统的核销 / 反核销记录。
  • 同步语义：Store.replaceHistory(records) 以数据源当前内容整体刷新快照行（旧快照行被替换），保证台账历史数据与数据源一致。
  • 自动刷新：页面按间隔（关闭 / 5 / 10 / 30 秒）比对变更指纹 Store.signature()，有变化才重新查询与渲染；切换页签、页面重新可见、其他标签页写入台账（storage 事件）时立即重查。
  • 接口契约：外部数据源 JSON 支持数组或 { records: [ … ] }，字段名兼容中文表头与英文键名（见 ③ 页说明）。
